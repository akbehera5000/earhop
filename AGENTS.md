# EarHop: guide for AI assistants (Copilot, Claude, others)

Read this file completely before changing anything. It explains what EarHop is, how both apps are built, how the
switching rules work, how to build and test, and the mistakes that already happened once and must not happen again.
`HANDOFF.md` has the full engineering history (section 7 lists every past bug and fix). `CHANGELOG.md` lists changes
by date. `README.md` is the user facing guide.

## 1. What EarHop is

One person, one pair of earbuds, three devices. The earbuds follow whichever device starts playing, the previous
device pauses, and taking an earbud out pauses (putting it back resumes). Everything runs on the local network.
There is no cloud, no account and no server.

| Device | App | Device name on the network |
| --- | --- | --- |
| Mac (macOS 13 or later, Apple silicon) | `mac/`, Swift menu bar app | `mac` |
| Android phone | `android/`, Kotlin app with a foreground service | `phone` |
| Android tablet (rooted) | the same APK | `tab` |

Earbuds: AirPods Pro 2 and Samsung Galaxy Buds2 Pro. One pair is active at a time (the "profile").

The device names must be exactly `mac`, `phone` and `tab`, and every device must have a different name. Two devices
with the same name caused the worst bug so far (see section 9).

## 3. Architecture in one picture

```
  every 0.25 s on each device
  ---------------------------
  read local facts:  playing?  in a call?  owner (earbuds connected here)?  ear reading (with source and confidence)
          |
          v
  HandoffCore.tick(snapshot)      pure state machine, identical in Swift and Kotlin, no Bluetooth, no threads
          |
          v
  actions: claim | release | pause | resume | info | safeMode
          |
          v
  Controller (Mac) / HandoffController (Android)   carries out actions: Bluetooth connect and release,
          |                                         media keys, switching stages for the UI, logging
          v
  status broadcast: {dev, ts, seq, playing, ear, owner, call} signed with HMAC-SHA256, about once a second and
  immediately on change, over Bluetooth LE and Wi-Fi UDP at the same time (setting "both", the default). Receivers keep
  the newest copy (PeerOrder) and feed it into their own tick.
```

The single most important design rule: **all switching decisions live in `HandoffCore`**. Platform code only gathers
facts and executes actions. Never add a decision rule to the platform code; add it to both cores and to both
simulators.

Mac specifics worth knowing:
* Owner check: `IOBluetoothDevice.isConnected()` for the active earbud address.
* Playing: the default output device is running AND (on macOS 14.2+) at least one non ignored app produces output.
  Output stays "busy" for about 2 seconds after a pause. That staleness is behind several past bugs.
* Pause and play: `MediaControl` sends explicit MediaRemote Pause or Play only. EarHop never presses the Play/Pause
  toggle on its own (only in the "Play/Pause key only" setting): browsers keep their output open after pausing, so any
  "still playing" check is wrong and the key would restart the music. The 6 s check after a command only logs.
* A call on the Mac means microphone and speaker busy together for 2 s (`CallDetector`). Microphone alone (dictation)
  is not a call.
* `--selftest` and `--snapshot` set `Config.readOnly = true` and `Log.toFile = false`. Keep it that way (section 9).

Android specifics worth knowing:
* Owner check: the A2DP proxy's `connectedDevices` contains a device whose name contains the profile filter

## 6. Protocol (must stay identical in Swift, Kotlin and Python)

Wi-Fi packet: one UDP JSON datagram to port 47474.

```
{"v":3,"dev":"phone","ts":<ms>,"seq":<int>,"playing":0|1,"ear":"both|one|none|unknown","owner":0|1,"call":0|1,"prof":"airpods|buds|","sig":"<hex>"}
canonical v3: "3|dev|ts|seq|playing|ear|owner|call|prof"   (v2 had no prof, v1 no call; both are still accepted)
sig = HMAC-SHA256(shared secret, canonical), lower case hex
refused: bad JSON, bad signature, |now - ts| > 30 000 ms
one sequence number per device, shared by both links (Bluetooth LE carries its low 16 bits)
receiver (PeerOrder): take a copy only if its sequence number is newer; an older or repeated copy only marks the device
as alive; a number more than 300 below the last means the device restarted and is taken
```

Test vectors (keep them passing in all three implementations):
* secret `test-secret`, canonical `1|mac|1700000000000|7|1|both|0` gives
  `389cb0b6b95b236ec9f8ee2a76263d87cf0f876d590b14c976960cbe424b4c00`
* canonical `2|mac|1700000000000|7|1|both|0|1` gives
  `8c0b895c231d9329540318f0d015d6cc3d2e1007950972ce05ef20bf82ba2b8f`
* BLE payload for that status at minute `1700000000000 / 60000` is `ea0000071707e997e90831cf5fb05515`
* canonical `3|mac|1700000000000|7|1|both|0|1|buds` gives
  `e0b6ceded3c4002c40a606404586e70634245c77a4f5aff28eedb1352866659d`, BLE payload `ea0000077752983dac7ce48782b05515`

BLE payload (16 bytes carried as one 128 bit service UUID):
`[0]=0xEA [1]=dev code (mac 0, phone 1, tab 2) [2..3]=seq [4]=flags [5..12]=first 8 bytes of HMAC(bytes 0..4 + 13..15)
[13..15]=minutes since 1970, low 24 bits`. Flags: bit0 playing, bits1 to 2 ear (0 unknown, 1 none, 2 one, 3 both),
bit3 owner, bit4 call, bit5 earbud profile known, bit6 profile is Galaxy Buds. Refused when the minute stamp is more than 2 minutes off. The BLE seq is the low 16 bits of
the device's main sequence number. Changing this format breaks the link until every device runs the new build.

Galaxy Buds frames: `0xFD, 2 length bytes (little endian, low 10 bits = id + payload + 2), id, payload, CRC16 XModem
(2 bytes), 0xDD`. Status id 0x61 (extended) and 0x60. Placement nibbles: 1 wearing, 2 idle, 3 or 4 in case, 0
disconnected. Checksums are checked; bad frames are only dropped after one good frame on that connection; lengths over
600 are junk. Offsets came from the MIT licensed omarchy-galaxy-buds-pro project (facts only, no code copied).

AirPods beacon: Apple manufacturer data, type 0x07; model little endian at bytes 5..6 (0x2024 is AirPods Pro 2 USB-C);
status byte bits 0x02 and 0x08 are the two in ear flags. Only beacons within 8 dB of the strongest smoothed signal
count (`Beacon.pick` / `BeaconPick.pick`), so other people's AirPods are ignored.

## 7. Switching rules (HandoffCore, both platforms)

States: `idle`, `ownerIdle`, `playingWithoutEarbuds`, `claimPending`, `ownerPlaying`, `ownerPausedByEarRemoval`,
`releasePending`, `lostOwnership`, `callPriority`, `safeMode`.

* **Claim** when: not owner, playing for at least `minPlay` (1 s), cooled down (2 s, doubling after each failure),
  nothing pending, not in safe mode, not claim blocked, no automatic gate, no fresh owner peer that is still busy,
  not outranked, ear reading in (or unknown when `requireEar` is off, the Android default).
* **Newest playback wins.** The owner blocks a claim only while it plays and started after us, or played within 2 s.
  Priority (default mac, tab, phone) only breaks a tie of 2.5 s.
* **Release** when the owner: has been out of ears 120 s; or is playing and another device started playing later
  (steadily for `minPlay`, after this device became owner): pause first, then release; or is idle for 2 s and another
  device started playing after this device became owner.
* **Claim blocked**: after releasing or losing the earbuds. Cleared after 2 s of real quiet, counted from 4 s after the block.
  While blocked, the device announces `playing=0` (`advertisedPlaying`), so its fading or speaker audio is never taken as a new start.
* **Lost the earbuds** (not by our own release): pause if audio played within the last 1.5 s, unless EarHop paused
  within 6 s or released within 15 s. Never a second Play/Pause.
* **Calls**: a peer with `call=1` makes the owner pause and release. A local call claims.
* **Ear removal**: pause on a trusted transition from in to out (one bud out counts when "pause when one is out" is on);
  resume within 120 s when back. Only medium or high confidence readings act. Right after EarHop's own pause, the
  resume trusts the pause for 3 s even if output still looks busy.
* **Safe mode** after 3 failed claims in a row. It ends by itself after 2 minutes, or at once when this or any fresh peer
  has the earbuds. Manual Take always works, also when gated or in safe mode.
* **Claim worker**: wait up to 8 s for a fresh owner peer to let go, then connect, verify ownership (Mac up to 15 s for
  Buds, Android 12 s per attempt for Buds), retry once.

Ear reading sources and confidence: `buds-rfcomm` high, `airpods-beacon` high on the Mac, on Android `none` high and
`one` or `both` medium (the second bud's removal can arrive 24 to 33 s late), `airpods-direct` high, `last-known` low
(20 s after a Buds channel closes), `assumed` low.


Current automated coverage: the Mac self test (protocol vectors, packet security, BLE payload, Buds frame fixtures,
beacon parsing and picking, call detection, 15 simulator timelines) and 55 Android tests (`HandoffSimTest` 15,
`EarPolicyTest` 14, `BudsProtocolTest` 18, `BlePayloadTest` 4, `AutoGateTest` 4).

The simulators (`SimTests.swift`, `HandoffSimTest.kt`) model several devices, one pair of earbuds and a fake clock,
including a toggle Play/Pause key, audio output that stays busy 2 s after a pause, audio that drops out for 0.75 s
when the earbuds leave, slow disconnects, and connects that fail while another device holds the earbuds. Any change
to the rules needs a simulator test on both platforms, and the new test must fail without the change.

Tooling notes:
* The Mac builds with the Command Line Tools, which have no SwiftUI macro plugin: `@State` does not compile. Use the
  `Box` ObservableObject with `@StateObject` (see `SettingsView.swift`).
* Very long Swift expressions (string concatenation, long `??` chains) hit "unable to type-check in reasonable time".
  Split them.
* `--snapshot <folder>` renders the popover in sample states to PNG (it captures its own window, no permissions needed).
* The Android emulator `earhop_test` has no Bluetooth: it only checks the UI and crashes.
* Bluetooth, real handoffs and the Buds channel can only be tested on the real devices. Ask the user for logs from
  every device involved (Copy log on each), with the times of what they did.

## 9. Mistakes that already happened: do not repeat them

1. **Never send a second Play/Pause.** The Mac key is a toggle; a second press after EarHop already paused restarts the
   music on the speakers. All pauses go through the core guards and `MediaControl`.
2. **Never trust "playing" right after a pause or a release.** Output stays busy about 2 s, and when the earbuds leave
   it drops and restarts on the speakers. That once looked like a new start and caused a 2 second ping pong.
3. **Never let test code touch the user's files.** A snapshot run once saved sample settings into the real config and
   replaced the secret and both earbud addresses. Test modes must set `Config.readOnly` and `Log.toFile = false`.
4. **Every device needs its own name.** The tablet kept the default "phone"; the Mac saw one "phone" flicking between
   playing and idle and every handoff became slow or bounced. Both apps now detect and report this.
5. **Close the Buds status channel before disconnecting.** An open RFCOMM channel made the disconnect take about 10 s.
6. **Do not judge an explicit pause too early.** A check after 2.5 s mistook stale output for a failed pause and
   pressed the toggle key. The check now runs after 6 s and is skipped if a newer command was sent.
7. **Packets arrive several times** (broadcast, directed broadcast, Bonjour, learned unicast). Always drop copies that
   are not newer.
8. **A wrong secret fails silently** unless reported. Keep the `rejection` reporting and the banners.
9. **Microphone alone is not a call.** Announcing a call takes the earbuds from every other device.
10. **Other people's AirPods** are in range in public places. Keep the signal strength filter.
11. **Speed changes cost reliability.** Lowering the 1 s minimum playback made flicker worse; the user explicitly
    prefers reliability over speed.
12. **Changing the BLE payload or the JSON canonical string breaks the other devices** until all are updated. Update
    Swift, Kotlin and `tools/earhop_tool.py` together, with new vectors.
13. **Never press the Play/Pause toggle automatically.** A "still playing after the pause" check once pressed it and
    restarted music on the speakers after every release, because browsers keep audio output open while paused.
14. **Both links deliver the same status.** Any new field or rule must go through `PeerOrder`, or a stale copy from
    the slower link will undo a newer one.
15. **Do not run the emulator's EarHop service on the owner's network with a real device name and a test secret.** The
    real devices report "packets from phone refused" for a few minutes. Use a name like `test` or stop it at once.
16. **Android blocks background clipboard reading (Android 10 and later).** Do not add hidden workarounds that read
    the clipboard without the user's action; sending from Android goes through the tile, notification, Share or the
    button. Never send items marked sensitive (Android) or concealed or transient (Mac password managers), and never log
    clipboard contents, only kinds and sizes. On rooted devices only, `ClipSync.startRootWatch` watches the system log as root for
    "Denying clipboard access to com.earhop.logger" and opens `ClipActivity` (auto) as root; that is the sanctioned way on rooted devices. Without root
    the same watch runs with READ_LOGS (granted once with adb) and the overlay permission (`startRootWatch(root = false)`).
17. **The phone never logs "Denying clipboard access"**, so the log watch cannot work there (checked with adb on
    2026-10-29), whatever log access is granted. The phone uses `ClipHelper`, started by the user from the Mac with
    `tools/phone_clip.sh`: it runs as the shell user (allowed to read the clipboard in the background), watches it, and
    hands each new text to `ClipHelperProvider` with the `content call` command. Do not switch that back to a local socket:
    SELinux denies shell to app socket connections (avc denied connectto). The provider refuses every caller except uid
    2000 (shell) and 0 (root). The helper stops when the phone restarts; it says hello every 60 s
    (`ClipSync.helperRunning`). Text over 100 KB makes the app open `ClipActivity` instead. The app's own clipboard
    listener must send with `auto = true`: on the phone it fires again whenever the clipboard is read, and without the
    duplicate check EarHop re-sent the same clip every second while it was on screen.
18. **The clipboard has its own method setting** (`clipTransport` on both apps: both, ble, wifi), separate from
    `transport` for the handoff. Also `clipAuto` (Mac), `clipReceive`, `clipExclude` (devices not sent to) and
    `clipNotify` (Mac).
19. **Android returns no clip at all while the phone is locked** (getPrimaryClip and getPrimaryClipDescription both null).
    Test the helper with the phone unlocked; "nothing readable" in `/data/local/tmp/earhop-clip.log` while locked is
    normal. Each clip read by the helper shows Android's "Shell pasted" toast once, so it must read only new copies
    that are not EarHop's own (label EarHop).
20. **Automatic switching can be off or paused on both apps** (`autoSwitch` and a non-saved pause on Mac, `auto` and
    `autoPausedUntil` on Android). Off or paused means no core tick at all; Take and Release still run.
21. **Earbuds are detected automatically** (`earbudsMode` "auto" on both apps): the pair connected to this device, else the
    `prof` of the fresh peer that has the earbuds, else no change. Android swaps the Buds channel or AirPods scanner live
    in `EarService.detectEarbuds`; never restart the service for it. A pair picked by hand sets the mode to manual.
22. **Do not count on the clipboard helper surviving a restart.** `ClipSync.watchHelper` restarts it through Shizuku when
    Shizuku runs as the shell user (uid 2000; as root the helper's shell package calls fail). Without Shizuku only a
    computer can start it (`tools/phone_clip.sh`).
23. **One automatic sending method at a time** (`clipAutoMethod`: root, helper, accessibility, read through
    `ClipSync.autoMethod`). Change it only with `ClipSync.setAutoMethod`, which stops the others; otherwise the root
    watch, the helper and the accessibility trigger can all send the same copy. The accessibility service is the owner's
    explicit choice (mistake 16): it never reads window contents and never logs event text. Do not show it as On from
    the settings string alone; Android keeps EarHop listed after a crash (`ClipAccessibilityService.state` needs the
    saved setting, Android's live enabled list and the bound service to agree). Installing a new APK on the phone switched
    the service off (seen on 2026-10-29): after every install, the owner has to turn it on again. The app cannot open the
    service's own settings page (OPEN_ACCESSIBILITY_DETAILS_SETTINGS is system only); it opens Accessibility scrolled to it.

24. **The Android app ships as a release build.** Never remove `-keep class com.earhop.logger.**` from
    `proguard-rules.pro`: `app_process` starts `RootBt` and `ClipHelper` by class name and several classes use
    reflection, so renamed classes break root switching and the clipboard helper without any build error. Sign only with
    the key from `~/.earhop/android-signing.properties`; never commit the key or its passwords, and never sign a
    release with another key, because every device would have to uninstall (and lose its settings) to update.

## 10. Working rules from the owner

* No em dashes anywhere, in chat or in files. Use commas, colons or full stops.
* Never publish or upload the code, logs, the shared secret, Bluetooth addresses or documents to public places.
* Ask before big work. Small, surgical changes; do not rewrite working parts.
* Be honest about what was tested. Say clearly when something is only covered by tests or builds and has not been
  tried on the real Mac, phone, tablet, AirPods or Buds.
* Reliability over speed.
* After a change: run `bash tests/run.sh`, rebuild the DMG or install with `build_app.sh`, copy the APK to `dist/`,
